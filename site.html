Практическая работа

ГЛАВНОЕ ПРАВИЛО ЭТОЙ РАБОТЫ

Мы меняем структуру базы, но не меняем данные. Восемь JSON-файлов — это источник, который выдал заказчик. Мы не удаляем оттуда строки, не переименовываем поля, не исправляем «странные» значения. Всё, что делаем: превращаем текстовые колонки в типизированные, расставляем ключи и связи.

Нашли в файле что-то необычное (дубль, пустое поле, ссылку на отсутствующую запись)? Не правим. Записываем в отчёт по работе и показываем преподавателю.

1. Словарик

Термины, которые дальше встречаются постоянно. Пробегитесь по ним один раз — дальше будет проще.

СловоЧто это простыми словами
ТаблицаОдна «картотека». Например, все заказчики.
Строка (запись)Одна карточка в картотеке. Один заказчик, один товар.
Колонка (поле)Одна характеристика у всех карточек. Например, «телефон».
Тип данныхПравило, что лежит в колонке: число, текст, дробное число. От типа зависит, сравнится 1000 с 200 как числа или как буквы.
Первичный ключ (PK)Номер карточки. Уникален, не повторяется, по нему карточку находят. В наших файлах PK заданы явно — их надо сохранить.
Внешний ключ (FK)Ссылка из одной таблицы в другую. В строке заказа лежит id заказчика — это FK на таблицу заказчиков.
Ссылочная целостностьПравило «нельзя ссылаться в пустоту». Нельзя записать заказ для заказчика, которого нет в базе.
Связь 1:МОдин заказчик — много заказов. Читается «один ко многим».
Связь 1:1Один пользователь — одна карточка заказчика.
CASCADE«Удали родителя — удали и детей». Удалили заказ — пропал его состав.
RESTRICT«Не дам удалить родителя, пока есть дети». Товар, который входит в спецификацию, удалить не даст.
CHECKОграничение-сторож: «в колонку quantity можно только число больше нуля».
ИндексАлфавитный указатель в конце учебника. Ускоряет поиск, но занимает место.

Работа состоит из трёх модулей, и они идут строго друг за другом: каждый следующий опирается на результат предыдущего.

ТРИ ВОЛНЫ РАБОТЫ

Волна 1 (БД-1): данные из файлов попадают в базу как есть — все колонки текстовые, ключей нет.
Волна 2 (БД-1): один скрипт пересобирает таблицы: типы, PK, FK, CHECK. Данные при этом переливаются, ничего не теряется.
Волна 3 (БД-2 и БД-3): к готовой базе подключаемся из Python и из SQL. Данные больше не трогаем вообще.

3.3. Шаг 1–4. Конвертация JSON в CSV

Шаг 1. Установите расширение JSON to CSV

В VS Code откройте панель расширений (Ctrl+Shift+X), в поиске наберите JSON to CSV — нужное расширение подписано автором Khaer Ansori — и нажмите Install.

Шаг 2. Откройте JSON-файл в VS Code

File → Open File… и выберите любой из восьми файлов с Google Drive, например Prices.json. Файл сначала скачайте в папку проекта: VS Code работает с файлами на диске, а не в облаке.

Шаг 3. Запустите конвертацию

Нажмите Ctrl+Shift+P, наберите Convert JSON to CSV и выберите команду с этим именем. VS Code откроет новый буфер без имени: в нём массив объектов уже разложен по строкам, значения разделены запятой, первая строка — заголовки колонок.

Шаг 4. Сохраните результат с расширением .csv

File → Save As…, имя файла держите равным имени таблицы: Prices.json → Prices.csv. Сохраняйте в папку проекта, рядом с остальными файлами данных.

ВАЖНО

Два свойства файла решают всё при импорте: кодировка и разделитель. Расширение пишет UTF-8 с запятой — не меняйте ни то, ни другое: диалог импорта в шаге 6 настроен ровно на эти значения, и кириллица проходит конвертацию без искажений.

Если после команды вместо таблицы в буфере оказалась одна строка из символов — исходный JSON не был массивом объектов. Проверьте, что скачали нужный файл.

Откройте вкладку Database Structure: импорт сделал все колонки текстовыми — у CSV типов нет, первичных и внешних ключей тоже нет. Это ожидаемо и пока не трогаем: типы, ключи и связи выставляются одним скриптом в разделе 3.7.

ПОЧЕМУ БЕЗ ТИПОВ НЕЛЬЗЯ РАБОТАТЬ

SQLite молча сравнит числа как строки, и цены отсортируются в порядке 1000 < 200 < 35 — по первому символу. Тип, поставленный один раз, экономит поиск таких ошибок в конце работы.

3.5. Шаг 8.5. Проверка исходных данных (обязательный шаг)

Прежде чем пересобирать таблицы, посмотрите на то, что импортировалось. Это не редактирование, а осмотр: мы ищем места, о которых надо написать в отчёте. Выполните на вкладке Execute SQL четыре запроса по очереди.

Запрос 1. Дубли первичных ключей. Первичный ключ не может повторяться, поэтому если дубль есть — пересоздание таблиц упадёт с ошибкой.

SELECT 'Products'    AS tbl, id, COUNT(*) AS cnt FROM Products    GROUP BY id HAVING cnt > 1
UNION ALL SELECT 'Materials',   id, COUNT(*) FROM Materials   GROUP BY id HAVING COUNT(*) > 1
UNION ALL SELECT 'Orders',      id, COUNT(*) FROM Orders      GROUP BY id HAVING COUNT(*) > 1
UNION ALL SELECT 'Sales',       id, COUNT(*) FROM Sales       GROUP BY id HAVING COUNT(*) > 1
UNION ALL SELECT 'Prices',      id, COUNT(*) FROM Prices      GROUP BY id HAVING COUNT(*) > 1
UNION ALL SELECT 'Specification', id, COUNT(*) FROM Specification GROUP BY id HAVING COUNT(*) > 1
UNION ALL SELECT 'Order_items', id, COUNT(*) FROM Order_items GROUP BY id HAVING COUNT(*) > 1;

Запрос 2. Ссылки в пустоту. Ищем строки, которые ссылаются на объект, которого нет в базе.

-- позиции заказов на несуществующий товар
SELECT DISTINCT oi.product_id AS missing_product
FROM Order_items oi
WHERE NOT EXISTS (SELECT 1 FROM Products p WHERE p.id = oi.product_id);

-- заказы на несуществующего заказчика
SELECT DISTINCT o.customer_id AS missing_customer
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Customers c WHERE c.id = o.customer_id);

-- спецификация на несуществующий товар или материал
SELECT 'product' AS what, s.product_id AS id FROM Specification s
WHERE NOT EXISTS (SELECT 1 FROM Products p WHERE p.id = s.product_id)
UNION ALL
SELECT 'material', s.material_id FROM Specification s
WHERE NOT EXISTS (SELECT 1 FROM Materials m WHERE m.id = s.material_id);

Запрос 3. Цены и скидки на несуществующие объекты. Здесь ссылка полиморфная, поэтому проверяем обе ветки.

SELECT p.id, p.item_id, p.item_type
FROM Prices p
WHERE (p.item_type = 'Товар'
       AND NOT EXISTS (SELECT 1 FROM Products  x WHERE x.id = p.item_id))
   OR (p.item_type IN ('Материал','Операция')
       AND NOT EXISTS (SELECT 1 FROM Materials x WHERE x.id = p.item_id));

SELECT s.id, s.item_id, s.item_type
FROM Sales s
WHERE (s.item_type = 'Товар'
       AND NOT EXISTS (SELECT 1 FROM Products  x WHERE x.id = s.item_id))
   OR (s.item_type IN ('Материал','Операция')
       AND NOT EXISTS (SELECT 1 FROM Materials x WHERE x.id = s.item_id));

Запрос 4. Какие значения вообще встречаются в колонках-справочниках. Это нужно, чтобы правильно написать CHECK в следующем разделе.

SELECT 'Customers.type'   AS col, type      AS val FROM Customers   GROUP BY type
UNION ALL SELECT 'Materials.type',  type      FROM Materials   GROUP BY type
UNION ALL SELECT 'Orders.status',   status    FROM Orders      GROUP BY status
UNION ALL SELECT 'Prices.item_type', item_type FROM Prices      GROUP BY item_type
UNION ALL SELECT 'Sales.item_type',  item_type FROM Sales       GROUP BY item_type;
ЧТО ДЕЛАТЬ С РЕЗУЛЬТАТОМ

Все четыре запроса вернули пусто. Отлично — переходите к разделу 3.7.

Что-то вернулось. Это не повод править файлы. Покажите результат преподавателю и зафиксируйте в отчёте. Дальше возможны два пути:

  • Дубль PK. Строк с одинаковым id в таблице-источнике быть не должно. Если он есть — это дефект исходных данных; в отчёте фиксируем, но в базе оставляем как есть.
  • Ссылка в пустоту. Она не помешает импорту, если на время пересоздания таблиц выключена проверка внешних ключей (в SQLite она выключена по умолчанию; в SQLite Browser за это отвечает галочка Edit → Preferences → Enforce foreign keys — её нужно снять на время раздела 3.7 и включить после).

3.6. Шаг 9. Таблица Users и базовый пользователь

Таблица Users не импортируется: она создаётся скриптом. Это таблица авторизации приложения, и её структура в точности соответствует модели, которую в модуле БД-2 будет читать SQLAlchemy: колонки login, password, role, full_name, is_locked, attempts.

Создайте таблицу Users и добавьте базового пользователя

В SQLite Browser перейдите на вкладку Execute SQL, вставьте скрипт и выполните его (кнопка с треугольником или F5), затем нажмите Write Changes.

CREATE TABLE Users (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    login       TEXT NOT NULL UNIQUE,
    password    TEXT NOT NULL,
    full_name   TEXT,
    role        TEXT,
    is_locked   INTEGER NOT NULL DEFAULT 0,
    attempts    INTEGER NOT NULL DEFAULT 0
);

НЕ ЗАБУДЬТЕ БАЗОВОГО ПОЛЬЗОВАТЕЛЯ

Без оператора INSERT база останется с пустой таблицей Users, и в приложение нельзя будет войти вообще: экран входа откажет даже администратору, потому что проверять логин будет не по чему. Пара admin / admin — базовый пользователь учебной работы.

Пароль в учебной версии хранится в колонке password в открытом виде — хеширование в этой работе не применяется. Прежде чем показывать работу кому-либо ещё, смените пароль базовой записи на свой.

3.7. Шаг 10. Пересоздание таблиц: типы, ключи, связи

Как это устроено и почему именно так

В SQLite Browser нет редактора внешних ключей. Первичный ключ, NOT NULL и UNIQUE правятся кнопками (Database Structure → Modify table), а связь объявляется только в описании таблицы оператором FOREIGN KEY … REFERENCES …. Поэтому импортированные таблицы пересоздают скриптом по одному шаблону:

  1. создаётся таблица-дубль с нужными типами и ключами (…_new);
  2. данные переливаются оператором INSERT INTO … SELECT …;
  3. старая таблица удаляется (DROP TABLE);
  4. дубль переименовывается в прежнее имя (ALTER TABLE … RENAME TO …).

Разберём шаблон на Order_items. Состав заказа зависит от заказов и товаров, поэтому обе колонки объявлены внешними ключами: order_id — с правилом CASCADE, product_id — с RESTRICT. Первичный ключ id сохранён как в исходном файле: задание прямо требует, чтобы структура принимала явные значения PK. Количество проверяется ограничением CHECK (quantity > 0).

ДВЕ ЛОВУШКИ, ИЗ-ЗА КОТОРЫХ СКРИПТ ПАДАЛ РАНЬШЕ

1. Колонка адреса. В CSV она называется addres — так она записана в исходном JSON. Скрипт ниже использует именно это имя. Если написать address, база ответит no such column.

2. Колонка user_id. В CSV её нет — она появляется только в проекте. Поэтому перед переливкой мы добавляем её командой ALTER TABLE Customers ADD COLUMN user_id INTEGER;.

Скрипт целиком

-- ============================================================
--  БД-1, шаг 10. Пересоздание таблиц: типы, ключи, связи.
--  Выполнять целиком на вкладке Execute SQL, затем Write Changes.
--  ВНИМАНИЕ: на время выполнения снимите галочку
--  Edit → Preferences → Enforce foreign keys.
-- ============================================================

-- 0) Готовим импортированные таблицы к переливке
ALTER TABLE Customers ADD COLUMN user_id INTEGER;   -- колонки нет в CSV

-- ------------------------------------------------------------
-- 1) Customers
-- ------------------------------------------------------------
CREATE TABLE customers_new (
    id       TEXT PRIMARY KEY,
    user_id  INTEGER UNIQUE REFERENCES Users (id) ON DELETE CASCADE,
    name     TEXT NOT NULL,
    inn      TEXT,
    addres   TEXT,                                   -- имя из CSV, не address!
    phone    TEXT,
    type     TEXT NOT NULL CHECK (type IN ('Покупатель', 'Поставщик'))
);
INSERT INTO customers_new (id, user_id, name, inn, addres, phone, type)
SELECT id, user_id, name, inn, addres, phone, type FROM Customers;
DROP TABLE Customers;
ALTER TABLE customers_new RENAME TO Customers;

-- ------------------------------------------------------------
-- 2) Products
-- ------------------------------------------------------------
CREATE TABLE products_new (
    id       INTEGER PRIMARY KEY,
    name     TEXT NOT NULL,
    category TEXT NOT NULL
);
INSERT INTO products_new (id, name, category)
SELECT id, name, category FROM Products;
DROP TABLE Products;
ALTER TABLE products_new RENAME TO Products;

-- ------------------------------------------------------------
-- 3) Materials
--    Значения для CHECK сверьте запросом 4 из раздела 3.5.
-- ------------------------------------------------------------
CREATE TABLE materials_new (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    type TEXT NOT NULL CHECK (type IN ('Материал', 'Операция'))
);
INSERT INTO materials_new (id, name, type)
SELECT id, name, type FROM Materials;
DROP TABLE Materials;
ALTER TABLE materials_new RENAME TO Materials;

-- ------------------------------------------------------------
-- 4) Orders
-- ------------------------------------------------------------
CREATE TABLE orders_new (
    id          INTEGER PRIMARY KEY,
    customer_id TEXT NOT NULL REFERENCES Customers (id) ON DELETE RESTRICT,
    order_date  TEXT NOT NULL,
    status      TEXT NOT NULL
                CHECK (status IN ('Новый', 'В работе', 'Отгружен', 'Отменен'))
);
INSERT INTO orders_new (id, customer_id, order_date, status)
SELECT id, customer_id, order_date, status FROM Orders;
DROP TABLE Orders;
ALTER TABLE orders_new RENAME TO Orders;

-- ------------------------------------------------------------
-- 5) Order_items
--    PK — id, как в исходном файле (задание требует принимать
--    явные значения PK). Колонки src_id в CSV нет.
-- ------------------------------------------------------------
CREATE TABLE order_items_new (
    id         INTEGER PRIMARY KEY,
    order_id   INTEGER NOT NULL REFERENCES Orders (id)   ON DELETE CASCADE,
    product_id INTEGER NOT NULL REFERENCES Products (id) ON DELETE RESTRICT,
    quantity   INTEGER NOT NULL CHECK (quantity > 0)
);
INSERT INTO order_items_new (id, order_id, product_id, quantity)
SELECT id, order_id, product_id, quantity FROM Order_items;
DROP TABLE Order_items;
ALTER TABLE order_items_new RENAME TO Order_items;

-- ------------------------------------------------------------
-- 6) Specification
-- ------------------------------------------------------------
CREATE TABLE specification_new (
    id          INTEGER PRIMARY KEY,
    product_id  INTEGER NOT NULL REFERENCES Products (id)  ON DELETE CASCADE,
    material_id INTEGER NOT NULL REFERENCES Materials (id) ON DELETE RESTRICT,
    qty         REAL    NOT NULL CHECK (qty > 0),
    UNIQUE (product_id, material_id)
);
INSERT INTO specification_new (id, product_id, material_id, qty)
SELECT id, product_id, material_id, qty FROM Specification;

3.9. Шаг 12. Индексы — «алфавитный указатель» базы

Индекс — это как алфавитный указатель в конце учебника. Нужна тема «Фотосинтез»: без указателя листаешь триста страниц, с указателем — открыл нужную сразу.

В базе ровно так же. Когда мы соединяем таблицы, нужно быстро найти строки заказа №47 в таблице Order_items. Без индекса СУБД читает таблицу подряд, строку за строкой; с индексом — прыгает сразу в нужное место.

Заметьте: на ваших 70–200 строках разницы не будет вообще. Индекс — это привычка делать правильно, она окупается на миллионах строк. Плата за индекс: немного места на диске и чуть более медленная вставка.

SQLite создаёт индексы автоматически только для PRIMARY KEY и UNIQUE. Для внешних ключей индекс нужно объявить самому — по этим колонкам идёт поиск при соединении таблиц.

4.2. Как SQLAlchemy заменяет список-заглушку

Для чтения models.py достаточно четырёх понятий. Дальше весь код модуля опирается только на них.

ПонятиеЧто это в нашем коде
DATABASE_URL и engineАдрес базы и созданное один раз «подключение»: create_engine(DATABASE_URL). Запись sqlite:///app.db означает: файл app.db лежит рядом с models.py. Закомментированная строка с postgresql — тот же адрес для другой СУБД.
Base и UserОписание таблицы на Python. Строка __table__ = Table("Users", Base.metadata, autoload_with=engine) говорит: не описывать колонки руками, а прочитать структуру готовой таблицы Users прямо из базы.
SessionРабочая сессия с базой: with Session(engine) as session. Внутри блока выполняются запросы, на выходе из блока сессия закрывается сама, даже если случилась ошибка.
select и commitЗапрос и подтверждение записи. session.scalars(select(User).where(User.login == login)).first() вернёт первую найденную строку или None; session.commit() фиксирует изменения. Без commit правки потеряются.
ГЛАВНАЯ МЫСЛЬ МОДУЛЯ

База данных заменила хранилище, а не интерфейс. Всю конвертацию строки таблицы в словарь собрала одна функция _to_dict, а экраны, как и прежде, вызывают find_user, add_user, unlock_user и не знают, список за ними или SQLite.

4.3. Шаг 17. models.py: модель пользователей на SQLAlchemy

Удалите старое содержимое со списком USERS и положите в файл модель, работающую с базой. Ни одна строка интерфейса не зависит от того, как модель хранит данные, — только от имён функций и возвращаемых значений, поэтому замена проходит без правки экранов.

from sqlalchemy import *
from sqlalchemy.orm import *

#DATABASE_URL = "postgresql+psycopg2://postgres:admin@localhost:5432/nmo"
DATABASE_URL = "sqlite:///app.db"
engine = create_engine(DATABASE_URL, echo=False)

class Base(DeclarativeBase):
    """Базовый класс моделей."""

class User(Base):
    __table__ = Table("Users", Base.metadata, autoload_with=engine)

def _to_dict(user):
    """Преобразует объект User в словарь для GUI."""
    if user is None:
        return None
    return {
        "id": user.id,
        "login": user.login,
        "password": user.password,
        "role": user.role,
        "full_name": user.full_name,
        "locked": bool(user.is_locked),
        "attempts": user.attempts,
    }

# ---------------------------------------------------------------------------
# Функции для работы с пользователями
# ---------------------------------------------------------------------------

def all_users():
    """Возвращает список всех пользователей."""
    with Session(engine) as session:
        users = session.scalars(select(User).order_by(User.id)).all()
        return [_to_dict(u) for u in users]

def find_user(login, password):
    """Ищет пользователя по логину и паролю. Если нет — None."""
    with Session(engine) as session:
        user = session.scalars(
            select(User).where(User.login == login, User.password == password)
        ).first()
        return _to_dict(user)

def user_by_login(login):
    """Возвращает пользователя по логину (или None)."""
    with Session(engine) as session:
        user = session.scalars(select(User).where(User.login == login)).first()
        return _to_dict(user)

def login_exists(login):
    """Есть ли пользователь с таким логином."""
    return user_by_login(login) is not None

def add_user(login, password, role, full_name):
    """Добавляет нового пользователя."""
    with Session(engine) as session:
        session.add(
            User(
                login=login,
                password=password,
                full_name=full_name,
                role=role,
                is_locked=0,
                attempts=0,
            )
        )
        session.commit()

def update_user(login, password, role, full_name):
    """Меняет пароль, роль и ФИО пользователя."""
    with Session(engine) as session:
        user = session.scalars(select(User).where(User.login == login)).first()
        if user is None:
            return False
        user.password = password
        user.role = role
        user.full_name = full_name
        session.commit()
        return True

def delete_user(login):
    """Удаляет пользователя."""
    with Session(engine) as session:
        user = session.scalars(select(User).where(User.login == login)).first()
        if user is None:
            return False
        session.delete(user)
        session.commit()
        return True

def register_fail(login):
    """Добавляет попытку входа. При 3 попытках блокирует пользователя.
    Возвращает True, если пользователь только что заблокирован.
    """
    with Session(engine) as session:
        user = session.scalars(select(User).where(User.login == login)).first()
        if user is None:
            return False
        user.attempts = user.attempts + 1
        if user.attempts >= 3:
            user.is_locked = 1
            session.commit()
            return True
        session.commit()
        return False

def reset_attempts(login):
    """Сбрасывает счётчик неудачных попыток входа."""
    with Session(engine) as session:
        user = session.scalars(select(User).where(User.login == login)).first()
        if user is None:
            return False
        user.attempts = 0
        session.commit()
        return True

def unlock_user(login):
    """Разблокирует пользователя и сбрасывает попытки."""
    with Session(engine) as session:
        user = session.scalars(select(User).where(User.login == login)).first()
        if user is None:
            return False
        user.is_locked = 0
        user.attempts = 0
        session.commit()
        return True

# ---------------------------------------------------------------------------
# Быстрая проверка: показать всех пользователей
# ---------------------------------------------------------------------------
if __name__ == "__main__":
    for user in all_users():
        print(user)

Разбор

  • Закомментированная строка с postgresql+psycopg2 — тот же DATABASE_URL, но для PostgreSQL: когда курс дойдёт до серверной базы, достаточно раскомментировать её и закомментировать строку sqlite — больше в коде не меняется ничего.
  • Функция _to_dict превращает объект-строку в словарь для GUI и по дороге переименовывает колонки: is_locked становится ключом locked, чтобы экраны читали прежнее имя.
  • Каждая функция открывает собственную сессию оператором with: соединение закроется гарантированно, даже при ошибке.
  • Функции записи (add_user, update_user, delete_user, register_fail, reset_attempts, unlock_user) завершаются session.commit(); функциям чтения (all_users, find_user, user_by_login) commit не нужен.
  • В конце файла — встроенная самопроверка: при прямом запуске модель печатает всех пользователей. Это самый быстрый способ убедиться, что база подключилась.

5. Модуль БД-3. Создание запроса: полная стоимость заказа

В модулях БД-1 и БД-2 мы собрали базу и подключили к ней приложение. Модуль БД-3 — это один SQL-запрос, зато самый тяжёлый в курсе: экзамен требует посчитать полную стоимость заказа покупателя.

Формулировка: запрос учитывает количество продукции в заказе и стоимость всех материалов и технологических операций, израсходованных на производство этой продукции, с учётом нормы расхода.

5.1. Из каких таблиц складывается стоимость

Заказ (Orders) состоит из строк состава (Order_items): какая продукция и в каком количестве заказана. Сама продукция в этой задаче деньгами не оценена: её стоимость складывается из материалов и технологических операций, потраченных на производство. Сколько единиц каждого материала и операции уходит на единицу продукции — говорит спецификация (Specification, колонка qty и есть норма расхода). Почём каждая единица материала и операции — знает таблица Prices: операции лежат в Materials с типом «Операция», а цены на них — в Prices строками с material_id, вместе с ценами материалов.

Ступень расчётаТаблицаПоле
Что и в каком количестве заказаноOrder_itemsquantity
Сколько единиц материала или операции уходит на единицу продукции (норма расхода)Specificationqty
Сколько стоит единица материала или операцииPricesprice
Стоимость строки заказаquantity × qty × price
Полная стоимость заказасумма стоимостей строк по заказу
ДВЕ МЫСЛИ, КОТОРЫЕ ВСЁ УПРОЩАЮТ

Первая. Технологические операции не требуют отдельной ветки расчёта: они лежат в тех же таблицах Specification и Prices, что и материалы, и попадают в сумму автоматически.

Вторая. Строки таблицы Prices, у которых заполнен product_id (цена самого товара), в этом запросе не участвуют: заказ оценивается по составу, а не по прайсу. Отсюда условие p.product_id IS NULL в соединении — оно отбирает только строки цен материалов и операций.

5.2. Собираем запрос по слоям

Самый надёжный способ понять запрос — собрать его из трёх кусков: сначала себестоимость одной единицы изделия, потом стоимость строки заказа, потом итог по заказу.

Слой 1. Себестоимость одной единицы изделия

Берём спецификацию изделия, к каждой строке подтягиваем цену материала или операции и перемножаем.

SELECT
    s.product_id,
    SUM(s.qty * p.price) AS unit_cost      -- себестоимость 1 изделия
FROM Specification s
JOIN Prices p ON p.material_id = s.material_id
WHERE p.product_id IS NULL                 -- только цены материалов и операций
GROUP BY s.product_id;

Результат — по одной строке на изделие, в колонке unit_cost — во сколько обходится производство одной штуки.

Слой 2. Стоимость строки заказа

Умножаем себестоимость единицы на количество, которое заказали.

oi.quantity * unit_cost

Слой 3. Полная стоимость заказа

Складываем стоимости всех строк одного заказа и сворачиваем по заказу.

GROUP BY oi.order_id

Всё вместе — это один запрос. Подзапросы ему не нужны: три соединения и GROUP BY.

5.3. Шаг 20. Итоговый запрос

Выполните запрос на вкладке Execute SQL

В результате придёт по одной строке на заказ, а в колонке total_cost будет стоять полная стоимость этого заказа.

SELECT
    oi.order_id,
    SUM(oi.quantity * s.qty * p.price) AS total_cost
FROM Order_items oi
JOIN Specification s ON s.product_id = oi.product_id
JOIN Prices p        ON p.material_id = s.material_id
WHERE p.product_id IS NULL
GROUP BY oi.order_id
ORDER BY oi.order_id;

5.4. Разбор по строкам

Строка запросаЧто делает
FROM Order_items oiСтартуем от строк состава заказа: в них уже есть и номер заказа, и количество, поэтому таблица Orders не нужна.
JOIN Specification sРазворачивает каждое изделие в его материалы и операции с нормой расхода. Строк станет много — это нормально: на каждое сочетание «строка заказа — материал» своя строка.
JOIN Prices pПриносит цену материала или операции.
WHERE p.product_id IS NULLОтсекает прайсовые строки товаров: считаем только по составу, а не по прайсу.
SUM(oi.quantity * s.qty * p.price)Три множителя — количество изделий в заказе, норма расхода на единицу и цена единицы. Их произведение и есть вклад строки в итог.
GROUP BY oi.order_idСворачивает все строки одного заказа в одну, SUM складывает вклады.
ПОЧЕМУ КОРОЧЕ УЖЕ НЕЛЬЗЯ

Заказ знает количество, но не состав изделия. Состав знает нормы, но не цены. Цены лежат в отдельной таблице. Поэтому три соединения — это минимум пути от количества до цены, и каждая строка запроса закрывает один разрыв между таблицами. Убрать любое из них — значит потерять либо количество, либо норму, либо цену.

КАК ЧИТАТЬ ЛЮБОЙ ЗАПРОС СО СВЁРТКОЙ

Читайте запрос в порядке: FROM и JOIN — из каких таблиц разворачиваем данные; WHERE — что отсекаем; GROUP BY — по чему сворачиваем; SUM и другие агрегаты — что складываем. Ошибка в любом из четырёх мест видна сразу: неверный JOIN даёт лишние строки, неверный GROUP BY — лишние группы, забытое условие в WHERE — завышенную сумму.

5.6. Шаг 21. Сверка: разложить заказ на строки

Прежде чем сдавать запрос, убедитесь, что итог сходится с ручным подсчётом. Этот запрос показывает каждую составляющую стоимости по заказу:

SELECT
    oi.order_id,
    oi.product_id,
    s.material_id,
    m.name AS material_name,
    m.type AS material_type,
    s.qty  AS norm,
    p.price,
    oi.quantity AS ordered,
    oi.quantity * s.qty * p.price AS line_cost
FROM Order_items oi
JOIN Specification s ON s.product_id  = oi.product_id
JOIN Materials     m ON m.id          = s.material_id
JOIN Prices        p ON p.material_id = s.material_id
WHERE oi.order_id = 1
ORDER BY s.material_id;

Сложите колонку line_cost — сумма должна совпасть с total_cost из итогового запроса до копейки.

КОНТРОЛЬНЫЙ ВОПРОС СЕБЕ

А что если у какого-то товара из заказа вообще нет строк в спецификации? Тогда JOIN Specification выбросит эту строку из результата, и стоимость заказа молча занизится. Проверить такие товары можно так:

SELECT DISTINCT oi.product_id
FROM Order_items oi
WHERE NOT EXISTS (SELECT 1 FROM Specification s
                  WHERE s.product_id = oi.product_id);

Пусто — хорошо. Если что-то вернулось, обязательно упомяните это в отчёте. Если по заданию такие товары должны учитываться как 0, замените JOIN Specification на LEFT JOIN и оберните произведение в COALESCE(…, 0).

Приложение В. Вопросы для самопроверки

Модуль БД-1

  1. Почему колонка Customers.id объявлена как TEXT, а не INTEGER?

    Ответ: значения вида 000000001 содержат ведущие нули; при переводе в число они обрежутся, и связь «заказ → заказчик» развалится.

  2. Что произойдёт, если объявить Orders.customer_id как INTEGER, а Customers.id оставить TEXT?

    Ответ: SQLite начнёт сравнивать числа со строками; соединение таблиц либо даст пустой результат, либо ошибку в момент создания ключа.

  3. Зачем в Prices ограничение «заполнена ровно одна из двух колонок»?

    Ответ: одна строка цены относится либо к товару, либо к материалу/операции. Если заполнить обе, непонятно, к чему относится цена; если ни одной — строка бессмысленна.

  4. Почему таблица Users создаётся после импорта, а не до него?

    Ответ: так порядок операций проще: сначала все данные, потом служебная таблица. Внешний ключ Customers.user_id → Users.id добавляется при пересоздании Customers, к этому моменту Users уже существует.

  5. Правило RESTRICT стоит на Specification.material_id. Что произойдёт при попытке удалить материал, который используется в спецификации?

    Ответ: SQLite откажет с FOREIGN KEY constraint failed. Сначала нужно убрать строки спецификации, ссылающиеся на этот материал.

Модуль БД-2

  1. Почему после session.add(...) обязательно нужен session.commit()?

    Ответ: без фиксации изменения останутся в сессии и не попадут в файл базы; при закрытии сессии они потеряются.

  2. Что делает строка __table__ = Table("Users", Base.metadata, autoload_with=engine)?

    Ответ: читает структуру готовой таблицы Users прямо из базы и связывает её с классом User, избавляя от ручного описания колонок.

  3. Почему app.py не пришлось править?

    Ответ: интерфейс работает только с именами функций и возвращаемыми словарями, а они не изменились. Это и есть разделение ответственности.

Модуль БД-3

  1. Почему в запросе нужен GROUP BY oi.order_id?

    Ответ: после соединений на один заказ приходится много строк (по одной на каждый материал и операцию). Группировка сворачивает их в одну строку на заказ, а SUM складывает вклады.

  2. Что случится, если убрать WHERE p.product_id IS NULL?

    Ответ: при определённой структуре данных соединение может поймать прайсовые строки товаров. Условие явно говорит, что считаем только состав, а не прайс. В нашей схеме его роль дублирует ограничение CHECK в Prices, но писать его всё равно полезно — запрос становится однозначным.

  3. Нужно ли отдельно учитывать технологические операции?

    Ответ: нет. Операции лежат в Materials с типом «Операция», их цены — в Prices по material_id. Они попадают в ту же сумму, что и материалы.

  4. Запрос вернул пустоту. С чего начать поиск причины?

    Ответ: с проверки «товары из заказов без спецификации» (раздел 5.6) и с проверки, что у материалов из спецификации есть строки в Prices.

Конец документа. Модули БД-1, БД-2, БД-3 — учебная версия практической работы.
